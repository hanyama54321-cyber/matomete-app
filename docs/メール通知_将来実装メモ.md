## 1. 経緯

本アプリの開発を始める以前、通知手段としてプッシュ通知とメール通知を並行して検討していた時期がある。その際、テスト送信用のメールアカウントを取得し、Firebase 上で試作を行った。

この試作の産物が `sendAnnouncementEmail` として本番プロジェクト（`anzen-matomete-app`）にデプロイされたまま残っていた。リポジトリの git 履歴には存在せず、コンソールまたは gcloud から直接デプロイされたもの。2026-07-24 の FCM 実装（Cloud Functions 初導入）の作業中に発見された。

プロジェクトが当初から Blaze プランだったのは、この外部メール送信のためだったと考えられる。

### 判明した構成から読み取れること

- 送信条件（`priority === 'high'` または `mustRead`）は、v0.3 のプッシュ通知が「必読お知らせ」を対象とする設計と実質的に同じ考え方だった。将来メール通知を実装する際も、この条件はそのまま踏襲できる
- 宛先の判定に `users.emailNotify` というフラグを使っていた。v0.3 では `users/{code}.notifyPrefs` にイベント種別ごとの ON/OFF を持たせているため、**将来は `emailNotify` を復活させず `notifyPrefs` に統合する**（第5章参照）

## 4-2. 退避・削除の自動実行手順（再利用可）

手動でコンソールを辿らず、Claude Code から CLI で実行する。以下は将来同種の作業（出所不明の関数の調査・退避）にも流用できる。

### 前提

`gcloud` にログイン済みで、プロジェクトが `anzen-matomete-app` に設定されていること。

```bash
gcloud auth login
gcloud config set project anzen-matomete-app
```

### 手順1：構成の保存（トリガー・環境変数・ランタイム）

ソース本体より先に、**どういう条件で発火する関数だったか**を記録する。将来の実装で最も価値がある情報。

```bash
mkdir -p docs/archive/sendAnnouncementEmail

gcloud functions describe sendAnnouncementEmail \
  --gen2 --region=asia-northeast1 --format=json \
  > docs/archive/sendAnnouncementEmail/function-describe.json
```

出力 JSON の以下を確認する。

- `eventTrigger` — 監視していた Firestore のパスとイベント種別
- `serviceConfig.environmentVariables` / `secretEnvironmentVariables` — 送信サービスの設定
- `buildConfig.runtime` — ランタイム
- `buildConfig.source.storageSource` — 次の手順で使うバケット名・オブジェクトパス

### 手順2：ソースの取得

`storageSource` の値を使って元アーカイブを取得し、展開する。

```bash
BUCKET=$(jq -r '.buildConfig.source.storageSource.bucket' docs/archive/sendAnnouncementEmail/function-describe.json)
OBJECT=$(jq -r '.buildConfig.source.storageSource.object' docs/archive/sendAnnouncementEmail/function-describe.json)

gcloud storage cp "gs://${BUCKET}/${OBJECT}" docs/archive/sendAnnouncementEmail/source.zip
unzip -o docs/archive/sendAnnouncementEmail/source.zip -d docs/archive/sendAnnouncementEmail/src/
```

### 手順3：認証情報の除去（必須）

**このリポジトリは GitHub Pages で公開されている。** 試作コードに SMTP パスワードや API キーが直書きされていた場合、そのままコミットすると外部に露出する。

コミット前に必ず走査する。

```bash
grep -rniE "password|secret|api[_-]?key|token|smtp|sendgrid|mailgun|nodemailer|gmail|credential" \
  docs/archive/sendAnnouncementEmail/src/ \
  --include="*.js" --include="*.json" --include="*.env*"
```

- 実際の値が見つかった場合は **`<REDACTED>` に置換**したうえで、何が入っていたかの種別だけを本メモに追記する
- `source.zip` はバイナリのため中身を走査できない。**ソース展開後は zip を削除する**（`rm docs/archive/sendAnnouncementEmail/source.zip`）
- `function-describe.json` にも環境変数の値が含まれうる。同様に確認・置換する

### 手順4：削除

手順1〜3が完了し、`docs/archive/` に内容が残っていることを確認してから実行する。

```bash
gcloud functions delete sendAnnouncementEmail --gen2 --region=asia-northeast1
```

削除後は `firebase deploy --only functions` で巻き添え削除の心配がなくなるため、`--only functions:名前,...` の個別指定運用は解除してよい。

### 手順5：記録

本メモの第2章に、`eventTrigger` の実際の監視パスと、使用していたメール送信サービス名を追記する。

## 5. 将来実装時の設計方針

### 別系統として作らないこと

これが最重要。v0.3 では、旧フォアグラウンド通知機構（`localStorage['fbNotifOptIn']` 系）を撤去して通知を FCM に一本化した経緯がある。メール通知を独立した仕組みとして追加すると、同じ二重管理の状態に戻る。

具体的には次の形にする。

- **`users/{code}.notifyPrefs` に「メールでも受け取る」の項目を追加する。** 通知種別ごとの ON/OFF は既存の枠組みをそのまま使い、送信手段の軸を1つ足すだけにする
- **既存のトリガー関数の中で、プッシュ送信の隣にメール送信を並べる。** `onAnnouncementNotify` などを分岐させず、`functions/lib/send.js` 相当の共通ヘルパーに送信手段を追加する形にする
- **送信対象の抽出ロジックを共通化する。** 対象者の解決・`notifyPrefs` による除外は、プッシュとメールで同じコードを通す

### 前提として整っているもの（v0.3 時点）

- `functions/` の Cloud Functions 基盤（Node 20、`asia-northeast1`、`maxInstances` 設定、Artifact Registry のクリーンアップ設定済み）
- `notifyPrefs` によるイベント種別ごとの ON/OFF
- 送信前の確認ダイアログ（`openNotifySendConfirm()`）
- 冪等制御（`notifiedAt` 方式）

これらの上に乗るため、承認が降りた時点での追加作業は送信処理の追加が中心になる見込み。

### 認証情報は絶対にコードへ直書きしないこと

試作版は Gmail アプリパスワードを `index.js` に直書きしていた。同じ実装をしないこと。

- Firebase Functions のシークレット機能（`defineSecret` / Secret Manager）を使い、値はコードにもリポジトリにも置かない
- ローカル開発時は `functions/.env`（`.gitignore` 済み）を使う
- 本リポジトリは GitHub Pages で公開されているため、直書きは即座に外部露出につながる

### 秘匿レベルの継承

プッシュ通知で定めたロック画面の秘匿レベル（設計書 9-1）は、メール本文にもそのまま適用する。特に**報告に関わる通知は、件名にも本文にも報告内容を含めない。** メールはロック画面より広く残るため、むしろ厳しく扱う。

### 匿名報告への扱い

匿名報告への回答通知は、FCM ではトピック購読により「送信先を記録しない」形で匿名性を守っている。**メールにはこの逃げ道がない**（宛先アドレスを持たなければ送れない）。したがって、匿名報告への回答通知をメールで送る機能は**作らない**か、匿名性を放棄することへの明示的な同意を投稿者から得る設計にする。ここは実装前に必ず再検討すること。
